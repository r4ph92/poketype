# Decisions, assumptions and unresolved questions

## Confirmed by the user

Online races against other players; players select a Pokémon racer; evolution requires grinding through races; random post-game drops grow the collection; top-down race visuals; fully retro old-game interface (first race mockup). The user requested mockups for stats, XP, collection and lobby, then this implementation handoff. Nickname support and badges were not finalized.

Decided on 2026-09-30, detailed in [PROGRESSION.md](PROGRESSION.md):

- Race XP depends on final place (150 / 120 / 100 / 80 for finishers, 40 unfinished, 0 abandoned) and each level has a fixed XP cost (`50 + 10 × level`, levels 5 to 50).
- The player picks a starter from a pool of ten. Post-race drops draw from every catchable Kanto base-form species by rarity tier.
- Rooms (2026-10-01, #37 and #40): a room holds at most 32 players (`gameConfig.rooms.capacity`); every room is public until unlisted rooms (#38). "Faire une course" joins the fullest waiting room with a free seat, the oldest on ties, and creates a public room with the player as host when none qualifies. During a race the map shows only the viewer's trainer and Pokémon; a leader bar above it shows the top three and the viewer (see [Public rooms, placement and live ranking](#public-rooms-placement-and-live-ranking-37-40)).
- Copyright: PokéType is a non-commercial educational school project. The README and a footer on every page say so and credit the rights holders; the site earns no money (see [Legal notice](#legal-notice)).

## Proposed defaults to unblock development

These are reversible recommendations, not client commitments. Put them in typed configuration and expose appropriate host settings.

- French initial UI locale, optional English UI; exercise language controlled separately by host. Mockup English labels become translations.
- Default normal race limit: 180 seconds, configurable. Preserve independent H4 inactivity and safety deadlines.
- Classic species/evolution are cosmetic; position comes from normalized typing progress, not species speed. Adjusted ranking is also displayed.
- Provide an explicit development seed/demo account near evolution to demonstrate the loop without changing live reward rules.
- Tentative duplicate policy: a duplicate species drop becomes 50 bonus XP for the racer. Revisit once the loop is playable; the user has not chosen this policy.
- Guests get session-scoped collection/XP too; new-account conversion atomically transfers both races and collection. Guest progression persistence is an extension of H2, not an explicit school requirement.
- XP and drops are settled by the server from the final result: abandoned races grant nothing, an unfinished result at the time limit grants 40 XP. Reward eligibility is separate from ranking.
- Readiness indicators are informational; only the host can start after valid settings and two humans are present. A requirement that everyone be ready is optional, not in SAL-3.
- Temporary host-disconnect baseline: preserve room for reconnect, prevent unauthorized launches, and close waiting room after a documented configurable grace period (proposed 60 seconds). Running race still follows H4; no surprise pause. Host transfer is later work.
- Technical room capacity is configurable and measured, not a permanent four-player cap. Set and document a conservative local default after load testing; show a useful admission error if capacity is reached. Set to 32 by the user on 2026-10-01 (#37); load not yet measured.
- Local password authentication has no reset UX. State this before signup, per AUTH-1; do not invent email collection.

Chosen by the scaffolding story (#11), not by the school brief.

- ORM and migrations: Drizzle ORM with drizzle-kit over the `postgres` (postgres-js) driver. Migrations are SQL files in `drizzle/`, applied by `scripts/migrate.ts`. The app uses one pooled client per process; move to a pooled connection string if deployed on serverless.
- Migration 0000 created `app_meta`, an empty table that only proved the migration pipeline. Migration 0001 (#12) drops it.
- Unit tests: Vitest, files in `tests/unit/`.
- E2E: Playwright (supports several browser contexts, needed for two-guest races), files in `tests/e2e/`. E2E runs against `TEST_DATABASE_URL`, never the development database.

The rule also flags string and template literals as direct branches of a ternary or `&&`/`||` in JSX children. - `agentRules: false` in `next.config.ts` stops `next dev` from writing an agent-rules block into CLAUDE.md.
- Application code is TypeScript only. The only JavaScript files are tool configs: `eslint.config.mjs` and `postcss.config.mjs`.

## Guest sessions (#12)

- Sessions are server-issued and stored in PostgreSQL behind an opaque cookie token, so a future real-time process can verify them with the same lookup (`src/server/sessions/session-store.ts`, free of Next imports). Push (#18) needs no separate process: the channel authorization route uses the same lookup.
- Cookie `poketype_session`: 32 random bytes in base64url, httpOnly, SameSite=Lax, path `/`, Secure in production. The database keeps only the SHA-256 hash of the token. Malformed, unknown, altered and expired values all resolve to "no session"; malformed values never reach the database.
- Identity and credential are separate tables: `guests` (trainer name, not unique) and `sessions` (token hash, expiry, link to the guest). Races and rooms will reference `guests.id`; guests are never hard-deleted while referenced. Accounts (#46) add a user reference to `sessions` and reuse the same cookie mechanism.
- H2 lifetime ("during the visit", provisional): the cookie has no `maxAge`, so closing the browser ends the session, and the server also expires it after 12 hours (`guestSessionLifetimeHours` in `src/config/game.ts`). The "Changer de dresseur" button deletes the session row and the cookie, for shared classroom computers where the browser stays open.
- Trainer name rule: NFC-normalized and trimmed, 2 to 16 characters (code points), starts with a letter or digit, then letters, combining marks, digits, spaces and hyphens. Only the server validates, so the French message is always the server's.
- No auth library for sessions. This departs from the suggestion in `ARCHITECTURE.md`: a library would add a dependency and a model we do not control for a single opaque-token lookup. An auth library may still be chosen for OAuth providers only (#53).
- `app_meta` is removed.
- Follow-ups: purge expired `sessions` rows (and orphan guests, never one referenced by `users`) on a schedule; rate-limit guest creation, which is open to anyone today.
- Names are validated on the server only; the input carries `maxLength` 100 (`maxSubmittedLength`) so a paste without JavaScript cannot exceed the 1 MB body limit, and the form stays `noValidate` so the French length message still comes from the server.

## Request protection and error pages (#12)

- Proxy POST rule (`src/proxy.ts`): a POST without an `Origin` header, with `Origin: null`, or with `Sec-Fetch-Site` of `cross-site` or `same-site` gets 403. Next lets a Server Action without Origin through, so this closes that gap. OAuth providers that return through a cross-site `form_post` will need an exception for their callback route in #53.
- Security headers (`next.config.ts`): CSP, `frame-ancestors 'none'`, `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, and HSTS in production only. The CSP allows `'unsafe-inline'` for scripts because Next inlines its bootstrap scripts; a nonce-based CSP would make every page dynamic and is deferred. `connect-src` adds the push websocket origin derived from `PUSHER_*` at build time (#18), for example `ws://localhost:6001` locally or `wss://ws-eu.pusher.com` in production.
- Error pages are French (`src/app/error.tsx`, `src/app/global-error.tsx`). Focus moves to the heading on mount so the error is read and the next Tab reaches "Réessayer". `error.tsx` reads its strings from `NextIntlClientProvider` in the root layout, limited to the `ServerError` and `Footer` namespaces so pages do not ship the whole catalogs. `global-error.tsx` renders outside the layout, so it imports the small slice in `messages/fallback/{fr,en}.json`; a unit test keeps the slice equal to the main catalogs.

## Rooms (#13)

- Model: `rooms` (uuid id, `host_guest_id`, `phase`, `revision`) and `room_members` (surrogate uuid id, room, guest, `joined_at`; unique per room and guest). H1 (provisional): the creator is the host, stored in `rooms.host_guest_id`. The `phase` check allows `waiting`, `countdown`, `racing`, `results` and `closed` (widened by migration 0003 in #14).
- Room ids are lowercase canonical uuids from `gen_random_uuid()`, parsed by `parseRoomId` (a branded `RoomId`) before any query, so a malformed id never reaches PostgreSQL. An uppercase id is treated as malformed: each room has one address.
- Commands and reads are split: `src/server/rooms/room-commands.ts` (writes, one transaction each, no Next imports) and `room-snapshot.ts` (read model). Room creation is a Server Action because it is a plain form; polled or pushed commands in later stories are route handlers that call the same command functions. Push (#18) left the command functions unchanged: the callers announce a committed change.
- Snapshot and revision: `RoomSnapshot` holds room id, phase, `revision` and members (`memberKey`, trainer name, `isHost`, `isViewer`). It never exposes guest ids and is null unless the viewer is a member. Every membership or phase change must bump `revision` in the same transaction; #14 will poll on it.
- Unknown, malformed and closed rooms all answer the same French 404 "Salle introuvable" (`src/app/rooms/not-found.tsx`). Since #14 a guest who is not a member joins instead (see below).
- `src/proxy.ts` rewrites `/rooms/*` paths with an undecodable segment (for example `/rooms/%`) to the static route `/rooms/unavailable`, which renders the same 404. Next answers 500 for such a dynamic segment, even after a rewrite to another dynamic value.
- No `loading.tsx` or Suspense boundary above the room page: streaming would commit a 200 status before `notFound()` runs, and the 404 status is required. The page loads through `enterRoom` (#14), cached per request so `generateMetadata` and the page share one join.
- A thrown notFound() is client-rendered by Next 16; unmatched URLs are server-rendered. Never add a loading.tsx above rooms/[roomId]: it turns room 404s into 200.
- Copy link: the client builds the address from `window.location`; if the clipboard is refused, the address is shown selected in a read-only field. Confirmation lasts `copyConfirmationSeconds` in `src/config/game.ts`.
- Follow-up: room creation has no rate limit, like guest creation; both belong in the same follow-up.

## Accounts (#46)

- Model: `users` (username, one `guest_id`) and `password_credentials` (one scrypt hash per user), separate so OAuth identities (#53, #54) can attach to the same user without a password. `sessions.user_id` is null for guests; a composite foreign key `(user_id, guest_id)` to `users(id, guest_id)` makes an account session always point at that account's own guest.
- An account is a player identity on top of a guest row: rooms, and later races and the collection, keep referencing `guests.id`. Signing up from a valid guest session attaches that guest to the new account (its trainer name becomes the username, its waiting rooms keep it and get a new `revision`), which is AUTH-4's attach step; #50 and #53 attach instead of copying. Without a guest session, signup creates a fresh guest. Signup takes an advisory lock on the presented token's hash and retires the guest's old sessions by expiring them instead of deleting them, so a concurrent second submission of the same session finds an expired row whose guest owns an account and gets `alreadyAccount` instead of minting another guest; every login lookup ignores expired rows. A purge job must delete expired `sessions` rows later; there is none yet. The replay rule is narrow: only a session row with no `user_id`, whose guest owns an account and that was retired within `replayWindowMinutes` (10, `gameConfig.account`) gives `alreadyAccount`; any other expired or unknown row counts as no session, so a browser with an expired account session can sign up again. `alreadyAccount` shows a form message asking to log in. The one exception is `completeReplayedSignUp`, for a no-JavaScript double click (two POSTs, the browser keeps only the second answer): when the row is a guest session retired within `replayCompletionSeconds` (60), its guest's account has the submitted username (any case) and the submitted password verifies through the hashing gate, a fresh account session is issued; any mismatch gives the plain `alreadyAccount` message with no hint of which part failed. It is a credential check, so #47's login throttle must cover it too. All expiry comparisons use the database clock.
- Signup expires every session of that guest and issues a new token, so a planted or stolen guest token never becomes an account session. Accepted consequence: if someone plants their own guest token in another browser, the races of that guest land in the new account, as with any guest transfer.
- Username rule: 3 to 20 characters from `A-Z a-z 0-9 _ -`, trimmed, unique in any letter case (unique index on `lower(username)`). The same pattern, built from `gameConfig.account.username`, is a database check; a unit test keeps the two equal. Provider names in #53/#54 must be mapped into it (truncate, replace other characters, add a numeric suffix on collision).
- Password rule: 8 to 128 characters counted in code points after NFC normalization, never trimmed; the confirmation must match exactly. Only the server validates, as for trainer names.
- Hashing: Node's built-in `crypto.scrypt` (N = 2^16, r = 8, p = 2, 16-byte salt, 32-byte key), stored in PHC format `$scrypt$ln=16,r=8,p=2$salt$key`, so the cost can be raised later without breaking stored hashes. Rejected: native argon2 addons (build step and platform binaries), bcrypt (cuts passwords at 72 bytes), `crypto.argon2` (experimental in Node 24). Argon2id is a follow-up once Node marks it stable. Passwords are NFC-normalized inside hashing and verification.
- Cost limits: one hash takes about 64 MiB and 0.3 s, so a per-process gate runs at most 2 at once with 8 waiting (`gameConfig.account.passwordHashing`); beyond that, signup answers "Beaucoup de joueurs créent un compte en ce moment…". Validation and a case-insensitive "name taken" check run before any hashing. Follow-up: per-IP rate limiting for signup and login (issue to create), together with the guest and room creation limits.
- Leaks: database errors thrown while an account is written are replaced by `DatabaseQueryError`, which keeps only the Postgres code, because Drizzle and postgres errors carry the query parameters and the failing row. `findSessionIdentity` never selects the credential table.
- "Ce nom est déjà pris" tells anyone that a username exists; criterion 3 of #46 asks for it. Login (#47) uses one generic error.
- Account sessions use the same cookie and lifetime rules as guest sessions (`gameConfig.account.sessionLifetimeHours`, no `maxAge`). On the play page an account sees "Se déconnecter" instead of "Changer de dresseur"; until #47 there is no way back into the account after logging out.
- The account bar (`src/features/account/AccountBar.tsx`) is rendered by each page, not by the root layout: a database query in the root layout would break the error pages during an outage. #21 merges it into the site header.
- Demo accounts: `npm run db:seed` creates Maya and Leo with the test passwords in `scripts/seed-accounts.ts`. It refuses a database whose host is not `localhost`, `127.0.0.1` or `::1` unless `SEED_ACCOUNTS=allow`. Whether demo accounts exist in production is a question for deployment. The Playwright global setup seeds the test database.
- The accounts migration was regenerated as `0004` after #14 took `0003` (a branch merged second deletes its migration, snapshot and journal entry and runs `npm run db:generate` again). Drizzle skips a migration older than the last one applied, so databases that had the old one are dropped and recreated.

## Logging in and out (#47)

- Login (`/login`, Server Action `logIn` -> `logInWithPassword` in `src/server/accounts/log-in.ts`): the submitted username is trimmed and lowercased by `loginUsernameKey` (`src/domain/username.ts`), which is both the lookup (`lower(users.username) = key`) and the throttle key. The password is never trimmed. The form checks only presence and the submitted-size cap; it never applies the sign-up rules, so "Maya!" gets the same generic answer as any wrong pair.
- One message for a wrong password, an unknown username and an account without a password credential: "Nom d'utilisateur ou mot de passe incorrect". An unknown username is verified against `dummyPasswordHash` (`src/server/accounts/dummy-password-hash.ts`), a hash of a random secret at the current scrypt cost, through the same hashing gate, so every refusal costs one full verification. A unit test keeps its cost equal to `currentCost`; regenerate it when the cost changes.
- Throttle table `login_failures` (`username_key`, `failed_at`, index on both, no foreign key so unknown usernames are counted under the key a real account would have). Rule (`isLoginLocked`, `src/domain/login-lock.ts`, `gameConfig.account.loginThrottle`): locked while the five latest failures of a key span at most five minutes and the latest is less than five minutes old. Ages come from the database clock. A locked attempt is refused with "Trop d'essais. Réessaie dans 5 minutes." without any hashing and is not recorded; a success deletes the key's rows.
- Reservation (`checkPasswordThrottled`, `src/server/accounts/login-throttle.ts`): a short transaction takes `pg_advisory_xact_lock(47, hashtext(key))` (two-key form, a separate space from the session-token locks), purges that key's rows older than window + lock, reads the lock state and, if open, inserts the failure row before any hashing. The password is then verified outside any transaction. Wrong keeps the row, success clears the key, busy (hashing gate full) deletes only the reserved row. Twenty parallel guesses therefore verify at most five. Rows of other keys are left for the purge follow-up together with expired sessions.
- Replayed sign-up (#46) is a credential check too: after the account's username matches, `completeReplayedSignUp` goes through the same reservation on that username's key. Locked gives `refused`, which shows the plain "already an account" message; a wrong password counts as a failure; a username mismatch records nothing.
- Known limit: anyone can lock an account for five minutes by typing wrong passwords for it (inherent to a per-username throttle). Per-IP limiting stays the follow-up named in #46.
- A successful login deletes the presented session row (a guest session, or nothing) and inserts a fresh account session in one transaction; the token is always new. The page and the action send an account straight to `/play`. With `?room=<id>` (the "Se connecter" link on the invitation step carries it), login returns to that room through `parseRoomId` and `destinationAfterEntry`, like guest entry, instead of a free return path.
- Gap (R8): logging in over a guest session deletes that session but leaves the guest's waiting-room memberships behind, the same as "Changer de dresseur" today. H2 transfers data only at account creation. Follow-up: leave or close those memberships when a session ends.
- Log-out: one route, `POST /logout` (`src/app/logout/route.ts`, `endSession`), used by the header button for accounts and by "Changer de dresseur" for guests through a plain `<form method="post">`. It deletes the session row, clears the cookie and answers 303 to `/`. Only POST is exported (GET 405) and the proxy refuses a POST without a trusted Origin (403). The play page no longer shows its own "Se déconnecter"; the header has it on every page.
- Back after log-out: the plain form post loads a new document, which drops the Next router cache that a soft Back would replay. Production pages are dynamic and Next sends `private, no-cache, no-store`, so the browser refetches them (proved against `next start` in `tests/e2e/log-out-production.spec.ts`, skipped without a build). `SessionSync` also reloads a page restored from the back-forward cache (`pageshow` with `persisted`) or loaded from the HTTP cache by a history navigation (`back_forward` with `transferSize` 0): the dev server sends only `no-cache` on purpose, and Chrome may keep `no-store` pages in its back-forward cache. A proxy `Cache-Control` header does not help: Next overwrites it on pages.
- Rooms: the snapshot member gets `hasAccount` (the guest has a `users` row). The waiting-room roster (`LobbyRoster`) shows "Invité" next to guests only; race and results views are unchanged. The play page shows "Invité" beside a guest's greeting again.
- Header on phones: the account bar takes its own row under the wordmark so "Compte : Maya" and "Se déconnecter" (or "Se connecter" and "Créer un compte") fit at 320–375 px.
- Seeding clears the seeded usernames' login failures, so a test run that locked Maya never leaves the next run locked out. Wrong-password tests use their own accounts; seeded Maya is used only for successful logins.

## Joining and live room updates (#14)

- Join on open (H1, provisional): opening `/rooms/<id>` with a guest session is the join intent. `enterRoom` in `src/app/rooms/[roomId]/load-room.ts` calls `joinRoom` (`src/server/rooms/room-commands.ts`): one transaction that locks the room row (`select … for update`), then answers `not-found` (unknown or closed), `already-member` (any other phase), `race-started` (not `waiting`), `full` (capacity reached, #37) or inserts the member with `on conflict do nothing` and bumps the revision. Re-opening never bumps the revision; parallel opens add one row.
- Why a write in a GET is safe here: it is idempotent and unique-backed, the session cookie is SameSite=Lax so a third party can only cause a join through a top-level navigation (the same as opening the link), `frame-ancestors 'none'` blocks framing, and link previews carry no cookie. Rule: never render an in-app `<Link>` to a room page without `prefetch={false}`. The alternative (a POST auto-submitted by the client) loses the no-JavaScript path and adds a round trip.
- Future POST routes (#15+): the proxy Origin/Sec-Fetch-Site guard, the guest from the session only, membership, host and phase checked inside the command, `Content-Type: application/json`, and only the needed methods exported. Every command locks the room row first, in the same order as `joinRoom`, and bumps `revision` through `bumpRevision`.
- A visitor without a guest session: waiting room → `/?room=<id>`; countdown, racing or results → the "La course a déjà commencé" page (200, no name step); unknown or closed → 404. The home page accepts `room` only as one string that passes `parseRoomId`; anything else (arrays, URLs, paths, uppercase) shows no invitation. The entry action re-parses the hidden `returnRoomId` field and rebuilds the target with `roomPath`, so a redirect never leaves the site or a room address.
- Refusal vs 404: a started race is a refusal page with a way back to `/play`, not a 404, because the room exists and the visitor was invited. "Closed" means gone for everyone, members included.
- Snapshot endpoint `GET /api/rooms/<id>/snapshot` (thin route handler): empty 401 for a missing, malformed or expired session before any room lookup; empty 404 for a malformed, unknown or closed room; empty 403 for an open room the session is not in (the session changed in another tab; opening the link would join it anyway, so this leaks nothing); otherwise the `RoomSnapshot` JSON (`roomId`, `phase`, `revision`, `members` with `memberKey`, `trainerName`, `isHost`, `isViewer`; no guest ids). All answers are `Cache-Control: no-store`. It never joins. Other methods answer 405 (403 from the proxy for a POST without a trusted Origin). The proxy answers an undecodable `/api/rooms/*` path with the same empty 404, because Next answers 400 there.
- Shared view types live in `src/domain/room-view.ts` with `parseRoomSnapshot`, so client code never imports server modules.
- Subscription boundary (`src/features/rooms/live/room-subscription.ts` holds the contract; `subscribe-to-room.ts` is the binding, `browser-polling-environment.ts` the DOM adapter): `subscribeToRoom(roomId, fromRevision, { onSnapshot, onConnectionChange, onGone, onSessionEnded, onNoLongerMember })` returns an unsubscribe function. The binding picks push with polling as keepalive and fallback when the page receives push settings, and short polling alone otherwise (see "Live updates by push (#18)"). Polling: one request at a time, `waitingPollIntervalMs` 1000 and `requestTimeoutMs` 1300 (a lost request is abandoned and asked again at once, so a snapshot arrives within 2 s of the network returning). Each consecutive timeout adds `timeoutBackoffStepMs` 100, capped at `maxRequestTimeoutMs` 1500 (all in `src/config/game.ts`), so a slow but alive connection still updates; the cap stays under 2 s because of the lost-request criterion. A connection whose every answer takes longer than 1.5 s waits for push delivery (#18), and a silently lost request is recovered within about 1.5 s plus one round trip; paused while the tab is hidden and asked again as soon as it is visible or back online; aborts the poller starts itself never report a lost connection. A failure, timeout or server error shows "Connexion perdue. On réessaie…" and retries at the same interval; the next full snapshot resyncs. Only a newer revision redraws the roster. 404 shows "Cette salle n'est plus disponible." (and hides the heading and invitation) and stops; 401 (`onSessionEnded`) and 403 (`onNoLongerMember`) send the tab to `/?room=<id>`.
- The live roster (`RoomRoster`, inside `WaitingRoomView`) sits in an `aria-live="polite"` region, not `role="status"`, which the copy-link confirmation already uses. The page wraps it in a `NextIntlClientProvider` holding only the Room keys it needs.
- CSP unchanged: `connect-src 'self'` covers same-origin polling (widened for the push websocket in #18).
- For #24 (leaving): join on open rejoins on any re-open (Back after leaving, reload, restored tab), so leaving must navigate with `replace` and/or record a "left" marker.
- Follow-ups: rate-limit polling and joins together with guest and room creation; room capacity (#41). Polling costs about one query per second per open waiting-room tab.
- E2E on the dev server: `tests/e2e/support/warm-up.ts` (Playwright `globalSetup`, skipped with `CI`) requests the main routes once so first-compile time does not exceed 5 s expectations.

## Starting a race (#15)

- `POST /api/rooms/<id>/start` (thin route handler) calls `startRace` (`src/server/rooms/start-race.ts`): one transaction that locks the room row, then answers `not-found` (unknown or closed), `not-member`, `not-host`, `already-started` (phase is not `waiting`) or `not-enough-players` (members counted inside the lock, fewer than `gameConfig.race.minimumPlayers`, 2 under H6), else inserts a `races` row and sets the phase to `countdown` with one revision bump. Row helpers (`lockRoom`, `isMember`, `countMembers`, `bumpRevision`) live in `room-rows.ts`, shared with `joinRoom`.
- Answers: 415 without `Content-Type: application/json` (checked first), 401 without a session, 404 for a malformed id or `not-found`, 403 for `not-host` and `not-member`, 409 for `not-enough-players`, 201 `{ "result": "started" }`, 200 `{ "result": "already-started" }` (a second click is not an error). Refusals are empty; every answer is `no-store`; only POST is exported (405 otherwise); the proxy still refuses a POST without a trusted Origin.
- `races` (migration 0004): `room_id`, `passage` (non-empty, copied in NFC), `starts_at`, `created_at`. The current race is the latest row of a room, read only in `countdown`, `racing` and `results`; no language column until #31. The snapshot gains `race: { startsAt (epoch ms), passage } | null`, visible only to members.
- Racing is derived, never written: the stored phase stays `countdown`; every client compares `startsAt` with its estimate of server time. #16's progress command refuses any report before `starts_at`, checked inside the room lock. #15 itself has no input and no progress endpoint, so criterion 5 is proved by the UI: no editable element before or after "Partez !", typing sends no request, the race row is unchanged.
- One clock: the app server sets `starts_at = request time + syncLeadMs (1500) + countdownSeconds (3) × 1000` and stamps `serverNow` on every snapshot answer. The poller reports `{ serverNow, sentAt, receivedAt }` (both from `performance.now`) through `onServerTime` on every answer, before the revision filter. `ServerClock` (`src/domain/server-clock.ts`) keeps the last `clockSampleWindow` (5) samples and uses the quickest round trip: offset = serverNow − midpoint. The client never reads `Date`, so a wrong or changed system clock has no effect. Push (#18) keeps this: a ping only triggers a snapshot fetch, so every answer still gives a sample.
- The 1.5 s lead lets a polling player see the start before the "3"; the view shows "Prépare-toi…" until 3 s remain, then 3, 2, 1, "Partez !". A player who learns late (slow poll, hidden tab, reload) sees only the seconds left, or "Partez !" directly, never a negative number. The first poll now runs at once (`firstPollDelayMs` 0) so a reload has a clock sample immediately.
- The countdown is `useRaceCountdown` (`useSyncExternalStore`): the timer only wakes the view at the next whole-second boundary; the step is always recomputed from `startsAt` and the clock. The server render and hydration show "Prépare-toi…".
- Passages (`src/config/passages.ts`, language `fr`) use letters, lowercase é è à ù ç ê, straight apostrophe, plain spaces, comma and period (unit-tested; widened by #22). No diaeresis, œ/æ or accented capitals, which are hard to find for ages 10–12. The passage renders in one text node with `lang="fr"`, whatever the interface language.
- Waiting room: the host sees "Lancer la course" with `aria-disabled` and the reason "Il faut au moins 2 joueurs" linked by `aria-describedby` while alone; while the request runs, "Lancement…" (also linked, not a live role, so the page keeps one `role="status"`); a failure shows a `role="alert"`. Other members see "L'hôte va lancer la course." and no button. When the race appears, `RaceStartView` replaces the waiting view, focuses its h1 and sets the "Course - PokéType" title.

## Typing and live progress (#16)

- Keystroke accounting (H3, provisional), pure in `src/domain/typing-progress.ts`. The typing area is a labelled `<textarea>` that cancels every plain `beforeinput` event and never reads its value (compositions: #22). One keystroke is an `insertText` or a committed composition (#22) whose data, NFC-normalized and without leading lone accents, is exactly one code point. If it equals the passage character at the current position it is correct and the position moves on by one; otherwise it is a rejected keystroke and the position stays (blocked entry, the JEU-2 baseline). Paste, drop, quoted paste, autocorrect replacement, several characters at once, composition text, line breaks and every deletion count as nothing: backspace never moves the position and never counts. A held key counts each repeated character, and each is checked against the passage, so repeats cannot inflate progress. Characters are compared by code point (`passageCharacters`, `passageLength` in `src/domain/passage.ts`, shared by client and server); passages are stored in NFC by #15.
- Free entry (#32) is not built. Dead-key and Option composition is built by #22, below.
- Counters are client-claimed. The server cannot see keystrokes, so it bounds only the order, the passage length and the speed of what a client reports.
- Report contract: `POST /api/rooms/<id>/progress` with `{ sequence, position, keystrokes, rejectedKeystrokes }`, cumulative non-negative integers up to 2^31 − 1, `sequence` from 1 and strictly increasing. The client sends the latest counters at most once per `progressBatchMs` (250), one request at a time, sending at once when the last report is older than that; each report is kept until the server acknowledges it and is retried after `progressRetryMs` (500) on a network error, timeout, 5xx, 429 or a 409 `not-started`. 200, 409 and 422 answers carry the stored row `{ result, lastSequence, position, keystrokes, rejectedKeystrokes, finishMs }`; on `stale` or `implausible` the reporter continues from the server's `lastSequence` and resends its local counters later, while the screen keeps the local position. 400, 401, 403, 404, 413 and 415, and 409 `race-over`, stop the reporter. A reloaded page resumes from `race.viewer` in the snapshot.
- Route order: 415 without JSON, 401 without a session, 404 for a malformed id, 413 when the body is over `maxProgressBodyBytes` (256, counted while reading the stream, not from `Content-Length`), 400 for a body that is not the four counters, then the command. Answers: accepted 200; not-found 404; not-member and not-participant 403; not-started, race-over, finished and stale 409; implausible 422; too-soon 429. Refusals without a stored row are empty; every answer is `no-store`.
- Command (`src/server/rooms/report-progress.ts`): first an unlocked read of the participant row refuses `finished`, `stale` (sequence not newer) and `too-soon` (less than half a batch after the last accepted report) without queueing on the room lock. Then, inside the room lock and with the time the request arrived: unknown or closed room → not-found; not a member → not-member (nothing about the race leaks); waiting room or no race → not-started; no participant row → not-participant; `results` → race-over; before `starts_at` (`acceptsTypingAt`, `src/domain/race.ts`) → not-started; already finished → finished; then `judgeProgressReport` (`src/domain/progress-report.ts`).
- Plausibility rules: sequence newer than the last accepted one; position, keystrokes and rejected keystrokes never go down; position at most the passage length; keystrokes − rejected = position (blocked mode); position at most `ceil(maxCharactersPerSecond × elapsed / 1000) + progressBurstAllowance` and keystrokes at most `ceil(maxKeystrokesPerSecond × elapsed / 1000) + progressBurstAllowance`, elapsed counted from `starts_at` (20 characters/s, 25 keystrokes/s, burst 10). The caps are cumulative, so many small reports cannot add up to a jump. A refused report changes nothing and bumps nothing, so no rival ever sees it. An accepted one updates the row, sets `finished_at` when the position reaches the passage length, and bumps the room revision.
- `race_participants` (migration 0006): primary key (race, guest), counters, `last_sequence`, `last_reported_at`, `finished_at`. `startRace` inserts one row per member in the same transaction as the race, so the participants are fixed at the start (#17 and #42 build on them). Checks keep every counter non-negative, keystrokes ≥ rejected and keystrokes − rejected ≥ position; the database allows `>=` for free entry (#32) while the judgement enforces equality for blocked entry.
- Account transfer (#46) keeps `guests.id` when it attaches a guest, so participant rows follow the account with no change.
- The finish time is `finished_at − starts_at`, measured by the server and shown with one decimal ("Terminé 6,8 s"). A player sees "Terminé" as soon as the last character is typed locally; the time appears from the accepted answer or the next snapshot, never from the client clock. Finishing does not change the room phase: racing stays derived from the clock, and #17 ends the race.
- Snapshot: in a race phase every member has `progress: { position, finishMs }` (position 0 until the first report); outside it `progress` is null. `race` gains `id` and `viewer` (the viewer's own counters and last sequence), so other players' keystroke counts are never sent during the race (#17 publishes each racer's error count once the race settles).
- Live view: while the snapshot holds a race with at least one unfinished member, the poller runs at `racePollIntervalMs` (250) instead of 1000 ms, so a rival sees new progress within about 0.6 s on a local server (well under the 1 s criterion). Cost: about four snapshot reads a second per racing tab, and up to four revision bumps (room row locks) a second per typist; fine at school scale. With push live (#18) the race is followed at a 1000 ms keepalive and each accepted report triggers one refetch per member instead. A hidden tab stops polling, so a backgrounded rival's view freezes until it is visible again. Two tabs of the same guest compete for the sequence number; the reporter resynchronizes on `stale`, but the counters of the two tabs can disagree and get refused until one tab is closed.
- View (`src/features/race/`): the passage shows the typed part in `success` green, the next character as a gold block with an ink underline, and a wrong expected character in `error` on `error-soft` with an error underline until the right key is typed (a wrong space shows `·`). The coloured copy is `aria-hidden`; a visually hidden plain copy is linked from the textarea with `aria-describedby`. The textarea is read-only and `aria-disabled` before "Partez !" and after the finish, so the layout never moves, and takes focus at "Partez !" (also after a reload mid-race). The roster shows each racer's percentage (floored) or "Terminé" with the time; it is not a live region. A separate visually hidden `role="status"` announces only the player's own 25/50/75 % milestones, their finish and each rival's finish.
- The rules version persisted with each race (ARCHITECTURE.md) is written at settlement by #17.
- Follow-ups for the end-of-week pentest: a guest can still make the room lock busy with valid reports spaced just over half a batch apart; rate-limit together with polling and room creation.

## French accents (#22)

- Full rules, the composition sequence and the keyboard matrix are in [keyboards.md](keyboards.md).
- One Unicode form: passages and typed text are NFC, counted by code point, so an accented letter is one character for progress, WPM and accuracy. "Decomposed" is accepted within one event only; a separate combining mark never fixes an earlier letter.
- A committed composition (`compositionend`) is one keystroke; text while a composition is open is ignored. A lone accent (`Sk`, `Mn`) is never a keystroke, so a dead key alone shows no error; an accent followed by a letter it cannot combine with is dropped and only the letter is judged.
- The typing area is uncontrolled (a controlled React value cancels compositions). A composition closes one macrotask after `compositionend` (`CompositionGuard`), so Safari's second insertion of the commit is not counted twice. The field is emptied once nothing is composing.
- No server change: the client still reports counters, and one accented letter is one keystroke, so `keystrokes − rejected = position` holds.
- No new message: a wrong accent is a rejected keystroke with the existing red mark and French typing hint (provisional, reversible).
- Keyboards are simulated in Chromium only (IME events through CDP; Safari order dispatched by hand); no physical keyboard has been checked yet. macOS press-and-hold is not supported.

## Race results (#17)

- Settlement point: the report that finishes the last unfinished participant settles the race in the same locked transaction (`settleWhenAllFinished`, `src/server/rooms/settle-race.ts`, called from `judge()` in `report-progress.ts`). It reads the participants once and does nothing while any of them has no `finished_at`. Otherwise it ends the race at the last finish and measures every racer from server-held values only (accepted position and counters, `finished_at − starts_at`), ranks them, writes `gross_wpm`, `score`, `accuracy` and `place` on each participant row, sets `races.ended_at` (the last finish time) and `races.rules_version`, and moves the room to `results`, all under the report's single revision bump. A second "last" report queues on the room lock and is refused (`finished`). Since #23 the guarded end (`update races … where ended_at is null returning id`) comes first and decides: only the call that ends the race writes the results and moves the room, so a repeated or concurrent call changes nothing and returns false. The time limit settles through the same `settleRace` (see "Time limit (#23)").
- Metrics (H3, provisional) are pure functions in `src/domain/race-results.ts`: gross WPM = typed characters / `charactersPerWord` (5) / minutes; score = max(0, WPM − rejected keystrokes / minutes); accuracy = (keystrokes − rejected) / keystrokes, 0 with no keystroke; errors = rejected keystrokes (blocked entry). The elapsed time is clamped to `gameConfig.scoring.minimumElapsedMs` (1000) so a finish inside the burst allowance never divides by zero.
- Ranking compares exact values, not the stored doubles: score as the integer fraction max(0, characters − 5 × errors) / elapsed ms, accuracy as (keystrokes − rejected) / keystrokes, both cross-multiplied in BigInt, then the earlier finish. Racers equal on all three share a place and the next place skips (1, 1, 3), since H3 says ties remain ties. Among tied racers the table orders by trainer name (code-point order, so server render and browser agree) then member key. Tie styling, the podium and abandoned statuses are #30; the time limit's "Non terminé" is #23.
- Rules version: `raceRulesVersion` (1) identifies the scoring code and is written with `ended_at` at settlement, not at the start; the database checks `(ended_at is null) = (rules_version is null)`. Changing `charactersPerWord`, the clamp or a formula bumps it.
- Frozen results: migration 0007 adds the four nullable result columns (all null or all set; `place >= 1`, accuracy in 0..1, WPM and score >= 0) and `races.ended_at`, `races.rules_version`. Snapshots read these rows and never recompute, so both pages and every refresh show the same values. The doubles are for display only.
- Display: WPM and score as whole numbers, accuracy as a whole percent through the existing `progressPercent` message, errors as a number, finish time with one decimal ("30,0 s"), all through the locale's number format. The place is a plain number in a "Place" column, not an ordinal; design.md's ICU ordinals belong to the podium (#30).
- Snapshot: `race.results` is a list of `{ memberKey, place, grossWpm, score, accuracy, errors, finishMs }` (no guest ids), null until the race has ended; `finishMs` is null for a racer the time limit stopped (#23). The server includes it only when the phase it read first is `results`, so a race that settles between the two reads shows its results from the next snapshot. The parser rejects results outside the results phase, a result for someone who is not a member, a non-finite or negative WPM or score, an accuracy outside 0..1 and a place below 1.
- View: `RaceResultsView` (`src/features/race/`) replaces the race view when results arrive (the reporter is disposed on unmount), focuses the "Résultats" heading and sets the "Résultats - PokéType" title, which is also the server-rendered title on refresh. The view is one level-1 `PixelPanel`; the standings are a `<table>` with a visually hidden caption, pixel column headers on `cream-deep`, mono data and the trainer name as row header; the viewer's row is gold and carries the "Toi" badge (the pixel-look gold check now accepts a `tr` with that badge, like the roster `li`). Tight cells and untracked headers fit seven columns in the page column even with 16-character names; below that the table scrolls sideways inside the panel, so its region is keyboard-focusable. "Retour à la page de jeu" (secondary `PixelLink`) is the only action until rematch (#42). The results view is a pixel-look state (look, focus, axe, catalog, screenshots at 320/375/1440). A results-phase room without stored results (only the test helper `setRoomPhase` makes one) keeps the race view.
- Results address = the room link. A non-member (guest or no session) gets "La course a déjà commencé" through join-on-open, with no names or scores; the snapshot answers the empty 403. No new route.
- Polling: at results the poller is back at the waiting interval. Since #23 `isRaceUnderway` is false in the results phase, because a race ended by the time limit keeps unfinished racers.
- A racer who never finishes no longer blocks the results: the time limit (#23) ends the race with unfinished racers, and abandon (#25) and idle detection (#27) will add earlier endings. A report is refused as `race-over` in the results phase or from the deadline on. `finished_at` is when the report arrived, up to about one batch (250 ms) after the last keystroke, so finish times and WPM are slightly pessimistic and equally so for everyone.
- Follow-ups for the end-of-week pentest: rejected keystrokes are client-claimed, so a crafted client reporting 0 gets 100 % accuracy and no score penalty; the speed caps still allow about 280 WPM on a 64-character passage; results now expose every racer's error count to the room (required by STAT-1), which #16 kept private during the race.
- Tests: `finishRaceInDatabase` (`tests/e2e/support/settlement.ts`) writes finishes and settles with the real `settleRace`; `startRaceInDatabase` takes an optional passage; helper start times are truncated to milliseconds, like the JavaScript dates the start command writes. `tests/e2e/full-race.spec.ts` plays the whole journey through the interface with no database shortcut and runs in the existing CI job.

## Time limit (#23)

- Every race stores `races.deadline_at` (migration 0009: added nullable, backfilled with `starts_at + 180 s`, then `NOT NULL`, checked `deadline_at > starts_at`). The start command writes `deadline_at = starts_at + gameConfig.race.timeLimitSeconds` (180, H4 provisional default, `raceDeadline` in `src/domain/race.ts`). The limit runs from "Partez !", so the countdown never eats typing time. No other server code recomputes a deadline from the config; the host-chosen duration (#33) only changes what the start command writes.
- No background job ends races. Whichever server path first sees the deadline passed settles it, inside the room lock: a progress report stamped at or after the deadline, a snapshot poll, or the room page load. `settleAtDeadline` (`src/server/rooms/race-deadline.ts`) calls `settleRace` with `ended_at = deadline_at`, so every path settles the same result whatever time the request arrived, and bumps the revision only when its guarded end won. Two requests at the deadline therefore settle once with one revision bump (command tests queue them behind the room lock).
- Unfinished racers are measured at the deadline from their accepted counters: gross WPM, score and accuracy use `deadline_at − starts_at` as the elapsed time, and they are ranked with everyone else by score, accuracy, then finish time (H3). An unfinished racer with a better score can rank ahead of a sloppy finisher. Their `finished_at` stays null; results show "Non terminé" in the time cell and the recap, and the viewer's encouragement is `unfinishedMessage` unless they placed first.
- Reports: under the lock, a report stamped at or after `deadline_at` (`isPastDeadline`, `>=`) is refused `race-over` (409) after settling the race if it is still running; a report 1 ms before is judged normally, and if it finishes the last racer the race ends at that finish. The unlocked quick path never refuses for the deadline. The last unsent batch (up to about 250 ms plus the network) therefore never counts; this is equally true for everyone.
- Reads: the snapshot route and the room page both call `loadRoomSnapshot` (`src/server/rooms/load-room-snapshot.ts`). It reads the snapshot as before (`findRoomSnapshot` stays write-free) and, only when the phase is running and the snapshot's `deadlineAt` has passed, settles under the lock and reads again, so a race still running costs no extra query. Players who closed their tabs see the results of a race ended at the limit when they reopen the room. This is the one call site push (#18) must publish from when a deadline settles.
- A deadline that passed never reopens a closed room: settlement only runs while the room is in `countdown` (or `racing`).
- Snapshot: `race.deadlineAt` (epoch ms, server clock) is sent with `startsAt`; the parser rejects a missing deadline or one not after the start.
- Timer: "Temps restant : 2:59" (`timeRemaining`, minutes and padded seconds) in the race status panel from "Partez !", computed from `deadlineAt` and the server clock only (`src/domain/race-remaining.ts`, `useRaceRemaining`), so two computers whose clocks differ by minutes show the same seconds (e2e: within 1 s with a 2-minute skew). It carries `data-remaining`, is not a second `role="timer"` and not a live region, so it never drowns the typing feedback. At 0:00 typing stops (`canType` also needs time left) and the hint says "Temps écoulé ! Les résultats arrivent." until the snapshot brings the results.
- The poller asks for a snapshot at the race deadline when that comes sooner than the next 250 ms poll, counted from when the last answer arrived so it never asks before the deadline on the server. Settlement therefore does not depend on poll cadence; push (#18) needs its own deadline trigger.
- Tests shorten a race only through its stored deadline (`startRaceInDatabase(roomId, startsInMs, { timeLimitMs })`), since the running server's config is fixed at build time. Command tests inject `now` and `reportedAt` instead of waiting.
- Out of scope: host-chosen duration (#33), inactivity and safety endings (#27), abandon (#25).

## Live updates by push (#18)

- Transport: the Pusher protocol, `pusher` on the server and `pusher-js` in the browser. Production uses a Pusher Channels app (Sandbox plan) that the user creates; local runs and CI use Soketi 1.6 (`quay.io/soketi/soketi:1.6-16-debian`, service `soketi` in `docker-compose.yml` and in CI), a real Pusher-protocol server, not a mock. Ably's Pusher adapter is the no-code escape hatch if the message quota bites. Rejected: PostgreSQL LISTEN/NOTIFY with server-sent events (Vercel function duration, one dedicated connection per listener), Ably's native SDK, Supabase Realtime and PartyKit (no offline CI, auth model mismatch, or a self-hosted server).
- Push is a hint, the snapshot stays the single source of truth. After a committed change the server publishes `revision` with `{ revision }` only on `private-room-<roomId>`; each member refetches its own member-gated snapshot, so the channel never carries room data and a subscription that outlives a session change leaks nothing.
- Publishing (`src/server/push/room-publisher.ts`, server-only): `announceRoomChange(roomId)` runs through `after()` from `next/server`, so after the response and therefore after the commit, never inside the room lock. It reads the room's current revision (one primary-key read) and triggers with a 2 s timeout (`gameConfig.push.publishTimeoutMs`); a failure is logged and swallowed, because polling still catches up. Callers: the progress route on `accepted`, the start route on `started`, the room page on `joined`. Room creation publishes nothing (nobody is subscribed yet). Command functions are unchanged.
- No server-side coalescing: every revision bump publishes. The per-player 250 ms report batch and the `too-soon` refusal already cap the rate. Each ping costs one snapshot read per member (about four a second per typist in a two-player race, growing with room size); the free-tier message quota is the main risk.
- Channel authorization: `POST /api/rooms/<id>/channel-auth` with JSON `{ socketId }`. The channel name comes from the path only. 404 when push is not configured or the room is malformed, unknown or closed; 415 for a non-JSON body; 401 without a session; 413 over 256 bytes; 400 for a missing or malformed socket id; 403 for a non-member; otherwise `{ auth }` from `authorizeChannel`. All `no-store`; the proxy Origin rule applies. Client events are disabled (`SOKETI_DEFAULT_APP_ENABLE_CLIENT_MESSAGES=false`, Pusher's default), so a member who publishes to the channel gets error 4301 and reaches nobody.
- Client (`src/features/rooms/live/`): `pusher-room-push.ts` subscribes with a custom authorizer (`authorize-room-channel.ts`) over `ws`/`wss` only, through one shared pusher-js client per tab (`shared-pusher-client.ts`, loaded on demand, released 1 s after the last room leaves). Live means connected and subscribed. `pushed-room-subscription.ts` drives the existing `RoomPoller`: a ping newer than the shown revision refreshes at once; a ping during a request in flight never aborts it and refreshes after its answer only if still behind; live changes refresh at once (catch-up after a reconnect in one round trip).
- Pace (`poll-pace.ts`): while push is live and trusted, polling keeps a 1000 ms keepalive in both phases (`gameConfig.push`), which keeps the clock fresh and the database-driven states (room gone, session ended) within #14's 2 s bounds. Without push, or after a poll finds a revision no ping announced, it is today's 250/1000 ms until the next ping proves push again. pusher-js activity and pong timeouts are 10 s and 5 s, so a silently dead socket is noticed within about 15 s, and a missed ping at the next keepalive poll.
- Settings (`src/server/push/push-settings.ts`): `PUSHER_APP_ID`, `PUSHER_KEY`, `PUSHER_SECRET`, then `PUSHER_CLUSTER` (Pusher Channels) or `PUSHER_HOST`, `PUSHER_PORT`, `PUSHER_USE_TLS` (Soketi). None set means polling only; a partial set throws at build and start. The room page passes a `PublicPushConfig` (key, websocket host, port, TLS; never the secret or app id) to the client as a prop, so there are no `NEXT_PUBLIC_` variables. The CSP origin is computed at build time, so `PUSHER_*` must be set before `npm run build` (CI sets them on the job). Playwright refuses to run in CI without them, since the push specs cannot pass on polling alone.
- Measured (`tests/e2e/push-delivery.spec.ts`): keystroke-to-rival-render p95 over a full 64-character race on the local production server with Soketi was 267–275 ms (max under 300 ms; most of it is the 250 ms report batch). Under heavy machine load the same test exceeds 500 ms because the server itself slows down. The 500 ms criterion on the real hosting is measured in #19 (deployment), with the Vercel function region next to the database.
- Deadline settles (#23) announce too: `loadRoomSnapshot` returns `hasSettledRace`, and the snapshot route and the room page announce when their read ended the race. The progress route announces on `race-over` as well as `accepted`, since a late report can be the one that settles. When it was not, the ping repeats a revision members already have and they drop it. While push is live, the poller still asks at the race deadline when that comes before the 1000 ms keepalive.

## Leaving and abandoning (#24, #25)

- Identity comes only from the session cookie: `POST /api/rooms/[roomId]/leave` and `/abandon` take no player from the body, so a request "naming Zoe" can only ever act on its sender. Both use the same guards as start (JSON content type, trusted origin in the proxy, 401 without a session, 403 for a non-member, 404 for an unknown or closed room) and run under the room lock, bumping the revision once per change. After push (#18) lands, each route publishes with one `after(...)` call once its command has resolved.
- Abandoning (`src/server/rooms/abandon-race.ts`): only a racer who has not finished, while the race runs (countdown or racing). It sets `race_participants.abandoned_at` (migration 0010; checked never set together with `finished_at`) and the racer keeps their counters. Abandoners never delay the end (H4): `settleWhenAllFinished` treats an abandonment like a finish, so the race settles at once when everyone else is done, ended at the latest finish or abandonment (never before the start). A second abandon is 200 `already-abandoned` through the route; a finished racer, a waiting room or a settled race answer 409.
- Progress reports from an abandoned racer are refused `abandoned` (409), on the unlocked quick path too, and the browser reporter stops on it.
- Abandoned racers have no place and no WPM, score or accuracy (the result columns stay null, which the existing all-null-or-all-set check allows). Settlement ranks only the others. Results list them after the ranked racers as "Abandon" with dashes (`RaceResultRow` is `abandoned: false` with metrics, or `abandoned: true` with the error count only), and the snapshot member progress carries `abandoned`. They are never shown as unfinished or placed last by score.
- Leaving (`src/server/rooms/leave-room.ts`): a non-host in the waiting room or the results is removed from the room, and may rejoin while it still waits. A non-host who leaves during a race abandons it and stays a member row: that is what lets the results keep listing them as "Abandon" (a deleted member would have no name or key to show), and `joinRoom` already refuses a room past its waiting phase, so nobody can enter or re-enter a race. Their client goes to /play and stops polling first, so a poll cannot send them back in.
- The host leaving closes the room in any phase (`phase = closed`), a reversible default until host transfer (#76). A running race is discarded without settlement: nobody is rewarded for a race the host cut short. A closed room answers 404 like an unknown one; members' open pages go to `/play?closed=1`, which shows "L'hôte a fermé la salle." once (the flag is dropped from the address on load) and replaces the former "room gone" panel.
- Confirmation: the host always confirms ("Si tu pars, la salle se ferme pour tout le monde."); a racer still racing confirms leaving and abandoning; leaving a waiting room or the results needs no confirmation. Confirmation uses a modal `<dialog>` that stays open with an error if the command fails.
- Push: the abandon route announces after a successful abandon, the leave route after a leave or a host close (`announceRoomChange`), so rivals see an abandon, a leave, a race settled by an abandon and a closed room by push. A leaver's subscription (push and polling) is torn down before navigating to /play.
- Members who stay remain in the room after the results (ready for the rematch, #42). A member who leaves during the results is removed, so their row disappears from the table other members see; revisit with #42 if the results should keep them.

## Public rooms, placement and live ranking (#37, #40)

- Capacity: `joinRoom` (`src/server/rooms/room-commands.ts`) counts the members under the room row lock and answers `full` once a waiting room holds `gameConfig.rooms.capacity` (32); a member still re-enters (`already-member`). Every join path goes through it: the room link, a list row and placement. A full room's link shows "Cette salle est pleine" with a link to the public rooms (title "Salle pleine - PokéType"). This replaces the old "conservative local default after load testing": 32 is the user's choice, load not yet measured.
- Public rooms (`findPublicRooms`, `src/server/rooms/public-rooms.ts`): waiting rooms below capacity, fullest first, then oldest, then id, at most `publicRooms.listLimit` (50). Full, racing, results and closed rooms are not listed, because none can be joined. The list and placement share this order.
- Placement (`placeInPublicRoom`, `src/server/rooms/room-placement.ts`): reads up to `rooms.placementCandidates` (10) public rooms without locks, then calls `joinRoom` on each in order. `joinRoom` locks the room and re-counts, so two players clicking for the last seat are serialized: one joins, the other gets `full` and moves to the next room, or creates one when the candidates run out. A player already in a candidate room stays there. The Server Action (`findRace`) and the home form both take the guest from the session (`redirectToPlacedRoom` is not a Server Action) and publish the room change by push after a join or a creation.
- "Faire une course" is the primary action of the trainer hub, with "Créer une salle" beside it as a secondary button. On the home page it is a second submit button of the trainer-name form (`intent=find-race`): the new guest is created and placed in one step. Enter keeps the plain "C'est parti !" submit. The invitation flow (`/?room=<id>`) does not offer it.
- The Race tab (`/play/race`) lists the public rooms with "Salle de {host}", "{n} / 32 joueurs", "En attente" and a "Rejoindre" link. The page renders the list on the server, then `usePublicRooms` asks `GET /api/rooms/public` every `publicRooms.refreshIntervalMs` (1000), one request at a time with a 1.3 s timeout, skipping turns while the tab is hidden, so a room appears or disappears within 2 s. A failure keeps the last list and shows "Liste indisponible. On réessaie…"; a 401 sends the tab home. Without a session the trainer layout already sends the visitor to the name form.
- Join links are `prefetch={false}`: opening a room page joins it (H1), so a production prefetch seated the viewer in every room scrolled into view (caught by `tests/e2e/public-rooms.spec.ts`). Any future link to `/rooms/<id>` must do the same.
- Race map: only the viewer, as their overworld trainer next to their Pokémon. Everyone stays in the side roster.
- Leader bar (`RaceLeaderBar`, ranking in `src/features/race/race-leaders.ts`): one start-to-finish track above the map with the top `race.leaderBarSize` (3) racers plus the viewer when outside them, so three or four markers. A marker is the place, the Pokémon and the trainer name, placed at the share of the text typed; it slides with a CSS transition (none under reduced motion). Ranking: finishers by finish time (a viewer who just finished locally comes after the timed finishers), then racers by accepted position, then those who abandoned; ties keep the roster's join order. The viewer's marker follows local typing at once, rivals follow the snapshot.
- Testing: public rooms are every waiting room in the database, so specs that read the list or place players run on a database of their own (`tests/e2e/support/isolated-database.ts`: created from the migrations, dropped afterwards), and the browser specs on a second production server (port `E2E_PORT + 4`).
- Known gap: a waiting room whose host closed the tab without leaving stays waiting, so it stays listed and can receive placed players. Room presence or idle closing is a follow-up.

## Interface language (#20)

- The interface language is the `poketype_locale` cookie (`fr` or `en`): HTTP-only, SameSite Lax, path `/`, one year, secure in production. It is its own name, not `NEXT_LOCALE`, and is read only in `src/i18n/request.ts`.
- Anything other than exactly `fr` or `en` resolves to French, so a tampered cookie never fails a page. `Accept-Language` is never read: a first visit is French whatever the browser says.
- The switch (`src/features/locale/`) is a form with one submit button per language and works without JavaScript. The Server Action writes the cookie only for a valid locale, then redirects back to the current path through `safeReturnPath` (`src/domain/return-path.ts`, reusable by #14), so the guest session and the room address are untouched.
- Every page is now rendered per request because the cookie is read on the server.
- The preference outlives the guest session on purpose ("Changer de dresseur" keeps the language); on a shared computer the next trainer sees the previous choice.
- `src/app/global-error.tsx` stays French: it renders outside the provider and cannot read the cookie.
- Both catalogs must hold the same namespaces, keys and placeholders (`tests/unit/i18n-catalog.test.ts`); later stories add both languages.
- Same passage for both languages (TXT-1) is not provable until races exist: verify in #15/#16. No room or command takes a locale.
- Other open tabs follow a switch: `LocaleSync` (mounted in the root layout) posts the rendered locale on a `BroadcastChannel` and calls `router.refresh()` when it receives a different one. A tab that misses the message, for example one restored from the back/forward cache, updates on its next load. #21 must keep `LocaleSync` mounted when it moves the switch into the trainer chip menu.
- The exercise language is a separate host setting (#31).

## Light and dark theme (#55)

- The choice (`light`, `dark`, or `system`) lives in the browser's local storage under `poketype-theme`, not in a cookie or the profile: it is a per-device comfort setting, needs no server round trip, and keeps pages free of a new request-time read. `system` removes the key.
- No stored choice means the page follows `prefers-color-scheme` through CSS alone; the attribute is only written for an explicit `light` or `dark`.
- A tiny inline script in the root layout's `<head>` (`src/features/theme/pre-paint-script.ts`) sets `data-theme` on `<html>` before the first paint. It runs in a `try/catch`, so blocked storage leaves the system setting in charge. The existing CSP already allows inline scripts.
- The switch (`src/features/theme/`) reads `data-theme` itself as its live state, so it works for the visit when storage throws; other tabs follow through the `storage` event.
- Tailwind v4 compiles `light-dark()` pairs in `@theme` to the `--lightningcss-light/-dark` toggle (checked in the built CSS), driven by `color-scheme`; no fallback block is needed.
- A wrong character is marked with a wavy underline against the caret's straight one, so it is told apart without colour.
